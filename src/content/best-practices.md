# บทที่ 9 — สรุป best practice

ทุกบทที่ผ่านมาสอนวิธีทำกับโปรเจกต์นี้ บทนี้ดึง **หลักการ** ที่อยู่เบื้องหลังออกมา
เพราะเครื่องมือเปลี่ยนได้ (พรุ่งนี้อาจย้ายจาก Vercel ไป Cloudflare, จาก GitHub Actions
ไป GitLab CI) แต่หลักการพวกนี้ใช้ได้เหมือนเดิม

แต่ละข้อบอกสามอย่าง: **หลักการ** / **พังยังไงถ้าไม่ทำ** / **ทำที่ไหนใน repo นี้**

---

## กลุ่มที่ 1 — ทำให้ผลลัพธ์คาดเดาได้

### 1. Reproducible build — build กี่ครั้งก็ได้ผลเหมือนเดิม

commit lockfile ลง git และติดตั้งด้วย `--frozen-lockfile` เสมอ

**ถ้าไม่ทำ:** CI ติดตั้ง dependency คนละเวอร์ชันกับเครื่องคุณ วันดีคืนดี library
ตัวหนึ่งออก patch ใหม่ที่มีบั๊ก CI แดงขึ้นมาเองทั้งที่คุณไม่ได้แตะโค้ดเลย —
แล้วคุณจะเสียครึ่งวันหาว่า "ผมทำอะไรผิด" ทั้งที่ไม่ได้ทำอะไรผิด

**ที่นี่:** `pnpm install --frozen-lockfile` ทุก job ใน [บทที่ 3](/docs/ci)

### 2. Single source of truth — ค่าเดียวกันเขียนที่เดียว

เวอร์ชัน Node อยู่ใน `.nvmrc` ไฟล์เดียว แล้วให้ CI และ Vercel อ่านจากที่นั่น

**ถ้าไม่ทำ:** เขียน `node-version: 22` ใน workflow, ตั้ง 20 บน Vercel, ใช้ 24 ในเครื่อง
→ build ผ่านสองที่ แดงที่สาม และไม่มีใครสังเกตจนกว่าจะพัง

**ที่นี่:** `node-version-file: .nvmrc` ใน [บทที่ 3.5](/docs/ci)

### 3. CI รันคำสั่งเดียวกับที่คุณรันในเครื่อง

ถ้า CI ทำอะไรที่คุณทำเองไม่ได้ เวลามันแดงคุณจะ debug ไม่ออก

**ถ้าไม่ทำ:** workflow มี step วิเศษที่ไม่มีใน `package.json` พอมันแดงต้องมานั่งอ่าน
YAML แกะว่ามันรันอะไร แล้วลอกมารันเองทีละบรรทัด

**ที่นี่:** ทุก step ใน `ci.yml` คือ `pnpm <script>` ที่มีใน `package.json` — [บทที่ 2.1](/docs/local-quality)

## กลุ่มที่ 2 — จับปัญหาให้เร็วและดัง

### 4. Shift left — ยิ่งเจอเร็ว ยิ่งถูก

ค่าใช้จ่ายในการแก้บั๊กเพิ่มขึ้นเป็นขั้น ๆ ตามที่มันหลุดไปได้ไกล:

```
เจอตอนพิมพ์ (editor)  →  วินาที
เจอตอน pnpm lint      →  นาที
เจอตอน CI             →  สิบนาที
เจอตอน review         →  ชั่วโมง (เสียเวลาคนอื่นด้วย)
เจอบน production      →  ครึ่งวัน + ลูกค้าเจอ + ต้องเขียน postmortem
```

**ที่นี่:** typecheck จับก่อน test, test จับก่อน build, ทั้งหมดจับก่อน merge

### 5. Fail fast, fail loud — อย่ากลบ error

ห้ามใส่ `continue-on-error: true` เพื่อให้ CI เขียว ห้าม `|| true` ท้ายคำสั่ง

**ถ้าไม่ทำ:** CI เขียวตลอดจนไม่มีใครดูมันอีก แล้ววันหนึ่งก็รู้ว่ามันไม่ได้ตรวจอะไรมาสามเดือนแล้ว
สิ่งที่แย่กว่า CI แดงคือ CI ที่เขียวโดยไม่มีความหมาย

**ที่นี่:** ไม่มี `continue-on-error` สักที่ และ `forbidOnly: !!process.env.CI`
กัน `.only` ที่จะทำให้ CI เขียวทั้งที่รันเทสตัวเดียว — [บทที่ 2.5](/docs/local-quality)

### 6. เก็บหลักฐานไว้ตอนพัง

อัปโหลด test report / log / screenshot เป็น artifact **เมื่อ job ล้ม**

**ถ้าไม่ทำ:** e2e แดงบน CI แต่ผ่านในเครื่อง คุณได้แค่ข้อความ `expected true, got false`
ไม่มีทางรู้ว่าตอนนั้นหน้าจอเป็นยังไง สุดท้ายต้อง push commit `debug: add console.log`
ไปเรื่อย ๆ ทีละรอบ ๆ

**ที่นี่:** `if: ${{ !cancelled() }}` + `upload-artifact` — [บทที่ 3.7](/docs/ci)
เงื่อนไขนี้สำคัญ เพราะ step จะถูกข้ามโดยอัตโนมัติถ้า step ก่อนหน้าล้ม
ซึ่งคือตอนที่คุณต้องการมันที่สุด

## กลุ่มที่ 3 — วางด่านให้ถูกที่

### 7. Gate ที่ merge ไม่ใช่ที่ deploy ⭐

**ข้อสำคัญที่สุดของทั้งคอร์ส** โค้ดเสียจะขึ้น production ได้ก็ต้องผ่าน main ก่อน
ปิดทางเข้า main ไว้ ที่เหลือจะง่ายขึ้นเยอะ

**ถ้าไม่ทำ:** ต่อให้ CD ซับซ้อนแค่ไหน ถ้ายัง push ตรงเข้า main ได้ก็ไร้ความหมาย
— branch protection + ทาง A ปลอดภัยกว่า ทาง B ที่ไม่มี branch protection

**ที่นี่:** [บทที่ 7](/docs/branch-protection)

### 8. อย่าเพิ่มความซับซ้อนที่ไม่ได้แลกมาด้วยประโยชน์จริง

ทุก secret คือของที่ต้องหมุน ทุก workflow คือของที่ต้องซ่อม

**ถ้าไม่ทำ:** ทีมสองคนทำเว็บ landing page แต่มี pipeline 6 workflow, 3 environment,
manual approval — พอมันพังไม่มีใครกล้าแตะ สุดท้ายก็ deploy ด้วยมือแอบ ๆ

**ที่นี่:** [บทที่ 6.0](/docs/cd-actions) บอกตรง ๆ ว่าเมื่อไหร่**ไม่ต้อง**ใช้ทาง B

### 9. Least privilege — ให้สิทธิ์เท่าที่ต้องใช้

ประกาศ `permissions:` ทุก workflow ให้แคบที่สุด

**ถ้าไม่ทำ:** action ตัวหนึ่งที่คุณ `uses:` โดนแฮ็ก (เกิดขึ้นจริงหลายครั้ง)
มันจะมี token ที่เขียน repo ได้ พร้อม push โค้ดอะไรก็ได้เข้ามา

**ที่นี่:** `contents: read` ใน `ci.yml`, ส่วน `release.yml` ที่ต้องเขียนจริงก็ให้
เฉพาะ `contents: write` + `pull-requests: write` — [บทที่ 3.4](/docs/ci)

### 10. ความลับต้องหมุนได้ scope แคบ และไม่เข้า git

token ตั้งวันหมดอายุ, จำกัด scope, เก็บใน secret store ไม่ใช่ในไฟล์

**ถ้าไม่ทำ:** token หลุดใน git history แล้วลบไม่ออก (ต้อง rewrite history ทั้ง repo
และถือว่ารั่วไปแล้วอยู่ดี) — และถ้า scope กว้าง คนได้ token ไปทำได้ทุกอย่างในบัญชีคุณ

**ที่นี่:** `.vercel/` อยู่ใน `.gitignore`, token scope เฉพาะ team, ตั้งวันหมดอายุ — [บทที่ 6.2](/docs/cd-actions)

## กลุ่มที่ 4 — พร้อมสำหรับตอนพัง

### 11. Rollback ก่อน debug

ของพังบน production → กลับไปเวอร์ชันที่ใช้ได้ก่อน แล้วค่อยหาสาเหตุอย่างใจเย็น

**ถ้าไม่ทำ:** นั่งไล่ log ไป 40 นาทีโดยที่ลูกค้าใช้งานไม่ได้ตลอดเวลานั้น
ความกดดันทำให้แก้ผิดซ้ำอีก แล้ว deploy ทับเข้าไปอีกรอบ

**ที่นี่:** Promote to Production ของ Vercel ใช้เวลาไม่กี่วินาทีเพราะ build เก่ายังอยู่ — [บทที่ 7.5](/docs/branch-protection)

### 12. Revert ไม่ใช่ force push

ยกเลิกด้วย commit ใหม่ ไม่ใช่ลบ history ทิ้ง

**ถ้าไม่ทำ:** เพื่อนร่วมทีมที่ pull ไปแล้วจะ git พังยกทีม และไม่มีร่องรอยว่า
เคยเกิดอะไรขึ้น — ซึ่งแปลว่าจะเกิดซ้ำได้อีก

**ที่นี่:** เปิด **Block force pushes** ใน ruleset — [บทที่ 7.3](/docs/branch-protection)

### 13. Deploy สิ่งที่ทดสอบแล้วเป๊ะ ๆ

ถ้าเป็นไปได้ ให้ deploy artifact ตัวเดียวกับที่ผ่านเทส ไม่ใช่ build ใหม่

**ถ้าไม่ทำ:** เทสผ่านบน Node 24 แต่ production build ด้วย Node 20 →
"เทสเขียวแต่ production พัง" ซึ่งเป็นอาการที่หาสาเหตุยากที่สุดแบบหนึ่ง

**ที่นี่:** `vercel build` + `vercel deploy --prebuilt` — [บทที่ 6.7](/docs/cd-actions)
(ข้อนี้ทาง A ทำไม่ได้ ซึ่งเป็นเหตุผลหลักข้อหนึ่งของการมีทาง B)

## Checklist เอาไปใช้กับโปรเจกต์อื่น

ก๊อปไปใช้ได้เลย ไม่ผูกกับ SvelteKit หรือ Vercel:

**ขั้นต่ำที่ทุกโปรเจกต์ควรมี**

- [ ] lockfile อยู่ใน git และ CI ใช้ `--frozen-lockfile` (หรือเทียบเท่า)
- [ ] เวอร์ชัน runtime เขียนไว้ที่เดียว ทุกที่อ่านจากตรงนั้น
- [ ] CI รันคำสั่งเดียวกับที่ dev รันในเครื่อง
- [ ] branch protection บน main: ต้องผ่าน PR + status check
- [ ] ปิด force push บน main
- [ ] `permissions:` แคบที่สุดในทุก workflow
- [ ] ไม่มี `continue-on-error` ที่ใส่ไว้เพื่อให้เขียว
- [ ] เก็บ artifact/log ตอน job ล้ม
- [ ] รู้วิธี rollback และเคยลองทำจริงแล้วอย่างน้อยหนึ่งครั้ง

**เพิ่มเมื่อทีมหรือความเสี่ยงโตขึ้น**

- [ ] ทุกการเปลี่ยนแปลงมีบันทึกว่าเปลี่ยนอะไร (CHANGELOG)
- [ ] release มี tag ที่ย้อนกลับมาหาได้
- [ ] deploy artifact ตัวเดียวกับที่เทส
- [ ] มีคนอนุมัติก่อนขึ้น production
- [ ] Dependabot / Renovate + dependency review
- [ ] pin action ด้วย SHA
- [ ] CODEOWNERS
- [ ] smoke test หลัง deploy

> **อย่าติ๊กหมดตั้งแต่วันแรก** เริ่มจากกลุ่มบน พอเจ็บจริงตรงไหนค่อยเพิ่มข้อจากกลุ่มล่าง
> pipeline ที่ดีคือ pipeline ที่โตตามความเจ็บจริง ไม่ใช่ตามรายการที่ลอกมา
