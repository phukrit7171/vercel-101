# บทที่ 0.5 — ศัพท์และพื้นฐานที่ต้องรู้ก่อน

บทนี้สำหรับคนที่ยังไม่ได้ทำงานสาย DevOps มาก่อน ถ้าคุณใช้ branch กับ pull request
เป็นประจำอยู่แล้ว **ข้ามไป[บทที่ 1](/docs/scaffold)ได้เลย** แล้วกลับมาเปิดตารางศัพท์
ตอนเจอคำที่ไม่รู้จัก

## 0.5.1 ทำไมต้องมี branch

ถ้าเคยทำงานแบบ "แก้โค้ด → `git commit` → `git push`" บน branch เดียวมาตลอด
คอร์สนี้จะขอให้เปลี่ยนวิธี เพราะ pipeline ทั้งหมดสร้างอยู่บนสมมติฐานว่า
**โค้ดต้องผ่านการตรวจก่อนเข้า main**

ปัญหาของการ push ตรงเข้า main:

```
คุณ push โค้ดที่ยังไม่ได้เทส → main พัง → เว็บ production พัง → คนใช้เจอ
                                   ↑
                        ไม่มีจังหวะไหนให้ตรวจเลย
```

**branch** คือสำเนาของโค้ดที่แยกออกมาทำงาน แก้อะไรก็ไม่กระทบของเดิม:

```bash
git switch -c add-search-button     # สร้าง branch ใหม่จาก main แล้วย้ายไปอยู่บนนั้น
# แก้โค้ด...
git add .
git commit -m "feat: เพิ่มปุ่มค้นหา"
git push -u origin add-search-button
```

ตอนนี้โค้ดคุณอยู่บน GitHub แล้ว แต่ **ยังไม่อยู่ใน main** — production ยังปลอดภัย

## 0.5.2 Pull Request คืออะไร

**Pull Request (PR)** คือคำขอว่า "ขอเอาโค้ดใน branch ของผมรวมเข้า main หน่อย"

มันไม่ใช่แค่ปุ่ม แต่คือ **พื้นที่ที่การตรวจสอบทั้งหมดเกิดขึ้น**:

```
┌─ Pull Request #12 ─────────────────────────────┐
│  add-search-button → main                       │
│                                                 │
│  📝 Files changed    ← คนอื่นมาอ่านโค้ดคุณตรงนี้ │
│  💬 Conversation     ← คุยกัน คอมเมนต์รายบรรทัด  │
│  ✅ Checks           ← CI รันอัตโนมัติตรงนี้      │
│  🔗 Preview URL      ← กดดูเว็บของ branch นี้ได้  │
│                                                 │
│  [ Merge pull request ]  ← กดได้ก็ต่อเมื่อผ่านหมด │
└─────────────────────────────────────────────────┘
```

วิธีเปิด PR: หลัง `git push` แล้ว GitHub จะขึ้นลิงก์ให้ในเทอร์มินัล
หรือเข้าหน้า repo แล้วจะมีแถบเหลือง **Compare & pull request** ขึ้นมา

**merge** คือการกดรวมโค้ดเข้า main จริง ๆ — จังหวะนี้แหละที่ทั้งคอร์สนี้พยายามปกป้อง

## 0.5.3 วงจรที่จะใช้ตลอดคอร์ส

```bash
git switch main && git pull        # 1. เอา main ล่าสุดมาก่อนเสมอ
git switch -c my-feature           # 2. แตก branch ใหม่
# แก้โค้ด
pnpm lint && pnpm check            # 3. ตรวจในเครื่องก่อน (บทที่ 2)
pnpm changeset                     # 4. บอกว่าเปลี่ยนระดับไหน (บทที่ 4)
git add . && git commit -m "..."
git push -u origin my-feature      # 5. push branch ขึ้นไป
# เปิด PR บน GitHub → รอ CI เขียว → กด Merge
git switch main && git pull        # 6. กลับมาเริ่มรอบใหม่
```

ทำซ้ำวงนี้ทุกครั้ง ไม่ว่างานจะเล็กแค่ไหน — แก้ typo คำเดียวก็ผ่าน PR

> **ทำไมไม่ยกเว้นให้งานเล็ก ๆ** เพราะ "งานเล็ก ๆ ที่คิดว่าไม่พังแน่" คือสาเหตุ
> ของ production incident จำนวนมาก และเพราะข้อยกเว้นทำให้กติกาไม่มีความหมาย

## 0.5.4 ศัพท์ทั้งหมดที่จะเจอ

### เกี่ยวกับ pipeline

| คำ                              | ความหมาย                                                                |
| ------------------------------- | ----------------------------------------------------------------------- |
| **CI** (Continuous Integration) | ตรวจว่าโค้ดพังไหม รันทุก PR                                             |
| **CD** (Continuous Deployment)  | เอาโค้ดขึ้น production รันหลัง merge                                    |
| **Pipeline**                    | ลำดับขั้นทั้งหมดตั้งแต่แก้โค้ดจนขึ้น production                         |
| **Gate**                        | ด่านที่ต้องผ่านก่อนไปต่อ เช่น "test ต้องเขียวก่อน merge"                |
| **Shift left**                  | ย้ายการตรวจสอบให้เกิดเร็วที่สุดเท่าที่ทำได้ ยิ่งเจอปัญหาเร็ว ยิ่งแก้ถูก |

### เกี่ยวกับ GitHub Actions

| คำ           | ความหมาย                                                                            |
| ------------ | ----------------------------------------------------------------------------------- |
| **Workflow** | ไฟล์ YAML ใน `.github/workflows/` ที่บอก GitHub ว่าให้ทำอะไรเมื่อไหร่               |
| **Job**      | หน่วยงานย่อยใน workflow แต่ละ job ได้เครื่องของตัวเอง                               |
| **Step**     | คำสั่งหนึ่งบรรทัดใน job รันเรียงจากบนลงล่าง                                         |
| **Runner**   | เครื่องเสมือนที่ GitHub เตรียมให้รัน job (ที่นี่ใช้ `ubuntu-latest`)                |
| **Action**   | โค้ดสำเร็จรูปที่คนอื่นเขียนไว้ เรียกด้วย `uses:` เช่น `actions/checkout@v5`         |
| **Secret**   | ค่าลับที่เก็บใน GitHub เข้ารหัสไว้ workflow อ่านได้ คนอ่านไม่ได้                    |
| **Variable** | เหมือน secret แต่ไม่ลับ มองเห็นค่าได้ ใช้เป็นสวิตช์เปิด/ปิด                         |
| **Artifact** | ไฟล์ที่ job สร้างขึ้นแล้วเก็บไว้ให้โหลดทีหลัง เช่น test report, ไฟล์ที่ build เสร็จ |
| **Matrix**   | การรัน job เดิมซ้ำหลายรอบด้วยค่าต่างกัน เช่น ทดสอบบน Node 20 และ 22                 |

### เกี่ยวกับการ deploy

| คำ                     | ความหมาย                                                                           |
| ---------------------- | ---------------------------------------------------------------------------------- |
| **Deployment**         | เว็บเวอร์ชันหนึ่งที่ถูกอัปขึ้นไปแล้ว แต่ละครั้งที่ deploy ได้อันใหม่               |
| **Production**         | เวอร์ชันที่คนทั่วไปเห็น อยู่ที่ URL หลัก                                           |
| **Preview deployment** | เว็บชั่วคราวของ branch นั้น ๆ ให้กดดูก่อน merge                                    |
| **Alias**              | ชื่อ URL ที่ชี้ไปหา deployment อันใดอันหนึ่ง "promote to production" คือย้าย alias |
| **Rollback**           | ย้าย alias กลับไปชี้ deployment เก่าที่ยังดีอยู่                                   |
| **Prerender**          | สร้าง HTML ทุกหน้าไว้ล่วงหน้าตอน build แทนที่จะสร้างตอนมีคนเข้า → เร็วและถูก       |
| **Hydrate**            | จังหวะที่ JavaScript เข้าไปทำให้ HTML ที่ส่งมาแล้วกดได้                            |
| **ISR**                | สร้างหน้าใหม่เป็นระยะ ๆ อยู่กึ่งกลางระหว่าง prerender กับสร้างสด                   |
| **Migration**          | สคริปต์เปลี่ยนโครงสร้างฐานข้อมูล ต้องรันให้ถูกจังหวะกับการ deploy                  |
| **Smoke test**         | เทสสั้น ๆ หลัง deploy ว่า "ยังหายใจอยู่ไหม" เช่น เปิดหน้าแรกได้ไหม                 |

### เกี่ยวกับเวอร์ชัน

| คำ                       | ความหมาย                                                                 |
| ------------------------ | ------------------------------------------------------------------------ |
| **semver**               | กติกาเลขเวอร์ชัน `MAJOR.MINOR.PATCH` เช่น `2.4.1`                        |
| ↳ **patch**              | แก้บั๊ก ของเดิมยังใช้ได้เหมือนเดิม → `2.4.1` → `2.4.2`                   |
| ↳ **minor**              | เพิ่มของใหม่ ของเดิมยังใช้ได้ → `2.4.1` → `2.5.0`                        |
| ↳ **major**              | ของเดิมพัง คนใช้ต้องแก้โค้ดตาม → `2.4.1` → `3.0.0`                       |
| **Tag**                  | ป้ายที่ปักไว้บน commit หนึ่ง ๆ เช่น `v0.2.0` ใช้ย้อนกลับมาหาได้          |
| **CHANGELOG**            | ไฟล์ที่บอกว่าแต่ละเวอร์ชันเปลี่ยนอะไรบ้าง เขียนให้คนอ่าน                 |
| **Conventional Commits** | กติกาเขียน commit message แบบ `feat:` / `fix:` ให้เครื่องอ่านได้         |
| **Lockfile**             | ไฟล์ที่จดว่า dependency แต่ละตัวเป็นเวอร์ชันไหนเป๊ะ ๆ (`pnpm-lock.yaml`) |

### เกี่ยวกับ git

| คำ             | ความหมาย                                                        |
| -------------- | --------------------------------------------------------------- |
| **Branch**     | สำเนาของโค้ดที่แยกออกมาทำงานโดยไม่กระทบของเดิม                  |
| **main**       | branch หลัก ตัวที่ deploy ขึ้น production                       |
| **Merge**      | รวม branch เข้าด้วยกัน                                          |
| **Squash**     | ยุบหลาย commit ใน PR ให้เหลืออันเดียวตอน merge — history สะอาด  |
| **Rebase**     | ย้ายฐานของ branch ไปต่อบน main ล่าสุด ทำให้ history เป็นเส้นตรง |
| **Revert**     | สร้าง commit ใหม่ที่ยกเลิกของเก่า — ปลอดภัยกว่าลบ history ทิ้ง  |
| **Force push** | เขียนทับ history บน remote — อันตราย เราปิดไว้ในบทที่ 7         |
| **CODEOWNERS** | ไฟล์ที่บอกว่าโค้ดส่วนไหนใครเป็นเจ้าของ ต้องให้คนนั้น review     |

### อื่น ๆ

| คำ                     | ความหมาย                                                                  |
| ---------------------- | ------------------------------------------------------------------------- |
| **Flake / Flaky test** | เทสที่บางทีผ่านบางทีไม่ผ่านทั้งที่โค้ดเหมือนเดิม — ต้องแก้ ไม่ใช่ปิด      |
| **Monorepo**           | หลาย package/แอปอยู่ใน repo เดียว                                         |
| **Supply chain**       | ห่วงโซ่ของโค้ดคนอื่นที่เราพึ่งพา (dependency, action) — จุดที่โดนโจมตีได้ |
| **Least privilege**    | ให้สิทธิ์เท่าที่จำเป็น ไม่ให้เกิน                                         |
| **Reproducible build** | build กี่ครั้ง ที่ไหน ก็ได้ผลเหมือนเดิม                                   |

## ✅ เช็คว่าผ่านบทนี้แล้ว

ลองทำวงจรในข้อ 0.5.3 หนึ่งรอบกับ repo นี้ — แก้ typo สักคำในไฟล์ใด ๆ ก็ได้:

```bash
git switch -c my-first-pr
# แก้อะไรสักอย่างเล็ก ๆ
git add . && git commit -m "docs: แก้ typo"
git push -u origin my-first-pr
```

แล้วเปิด PR บน GitHub ดู ถ้าเห็นแท็บ **Checks** มี CI กำลังรันอยู่ = พร้อมไปต่อ
